# Nutritional Deficiency Predictor

Full-stack app: FastAPI backend serving real trained scikit-learn models
(Iron / Calcium / Vitamin D deficiency risk), and a static frontend
dashboard that calls it.

```
app/
├── backend/
│   ├── ICD_Project.ipynb     # YOUR notebook — the live source of truth
│   ├── notebook_runtime.py   # safely executes the notebook, extracts the clean df
│   ├── train.py              # runs the notebook + trains + saves models
│   ├── main.py                # FastAPI app + background auto-retrain watcher
│   ├── requirements.txt
│   └── models/                 # generated by train.py (already included, pre-trained)
│       ├── Iron_Deficiency_Risk_model.joblib
│       ├── Calcium_Deficiency_Risk_model.joblib
│       ├── Vitamin_D_Deficiency_Risk_model.joblib
│       ├── scaler.joblib
│       ├── label_encoders.joblib
│       ├── feature_order.json
│       └── metrics.json
└── frontend/
    └── index.html              # served by the backend at "/"
```

## Run it

```bash
cd backend
pip install -r requirements.txt

# optional — models/ is already included pre-trained, only needed to retrain:
python train.py

uvicorn main:app --reload --port 8000
```

Open **http://localhost:8000** — the dashboard is served from the same
FastAPI app, so there's no separate frontend server or CORS config needed.

## The notebook IS the source of truth

`backend/ICD_Project.ipynb` is your original notebook, included as-is.
The backend runs it directly:

- `train.py` executes `ICD_Project.ipynb`'s code cells in order, and pulls
  out the dataframe at the exact moment the three deficiency-risk target
  columns exist and the data is clean — right before the notebook label-
  encodes the categorical columns. (This uses a custom runtime,
  `notebook_runtime.py`, instead of the notebook's own encoder/scaler
  objects, because the notebook reuses a single `le` / `scaler` variable
  across all three targets, so those specific objects aren't safe to
  reuse for serving — see the docstring in that file for details.)
- On top of that dataframe, `train.py` applies its own fixed, robust step:
  per-column `LabelEncoder`s, one `StandardScaler`, and a
  `RandomForestClassifier(class_weight="balanced")` per target — chosen
  over a plain Decision Tree because its `predict_proba` is graded
  (needed for Low/Moderate/High risk bands) instead of near-binary.

**Edit the notebook, save it, and the website updates itself** — a
background watcher in `main.py` polls `ICD_Project.ipynb`'s modified time,
and when it changes:

1. re-executes the notebook via `train.py`,
2. regenerates `models/*.joblib`,
3. hot-swaps the new models into the running server — no restart needed.

Track progress at `GET /api/model-status`:

```json
{ "status": "idle", "last_trained_at": "2026-08-23T16:47:05Z", "last_error": null, "version": 2 }
```

`status` is `idle`, `training`, or `error` (a failed retrain keeps the
previous working model live; `last_error` explains what broke). The
frontend polls this every 4 seconds and shows a badge next to the title.

**What kind of edits work automatically:** changing a rule threshold (e.g.
`Protein < 60` → `Protein < 55`), the dataset generation parameters, the
cleaning logic, or adding a new engineered feature column — anything that
happens before the notebook's own label-encoding cell. Renaming the three
target columns, or the `df` variable itself, will break extraction (the
watcher's error message will say so). Adding a feature column the frontend
form doesn't have a field for will train fine but won't be fillable from
the UI until the form is updated to match.

To retrain manually instead of waiting for the watcher:

```bash
cd backend
python train.py                       # uses ICD_Project.ipynb by default
python train.py --notebook other.ipynb # or point at a different notebook
```

## API

`POST /api/predict`

```json
{
  "Age": 34, "Gender": "Female", "Diet_Type": "Vegan",
  "Calories": 1800, "Protein": 45, "Vegetable_Intake": 1.5,
  "Fruit_Intake": 1.0, "Dairy_Intake": 0.5, "Water_Intake": 2.0,
  "Meal_Frequency": 3, "BMI": 22, "Physical_Activity": "Low"
}
```

returns

```json
{
  "ok": true,
  "results": {
    "iron":      { "target": "Iron_Deficiency_Risk",      "risk_level": "High", "probability": 0.9629, "predicted_class": 1 },
    "calcium":   { "target": "Calcium_Deficiency_Risk",   "risk_level": "Low",  "probability": 0.0638, "predicted_class": 0 },
    "vitamin_d": { "target": "Vitamin_D_Deficiency_Risk", "risk_level": "High", "probability": 0.9459, "predicted_class": 1 }
  }
}
```

`GET /api/metrics` — accuracy/precision/recall/f1 for every candidate model
per target (Logistic Regression, Decision Tree, Random Forest), as computed
by `train.py`.

`GET /api/features` — the exact feature order and categorical dropdown
options the model expects, useful if you rebuild the frontend.

## Notes on the model

- Feature set and target-generation rules match the original ICD notebook
  exactly (Iron: `Protein < 60 & Vegetable_Intake < 2.0`; Calcium:
  `Dairy_Intake < 1.5 & Age > 50`; Vitamin D: `Fruit_Intake < 1.5 &
  Physical_Activity == 'Low'`).
- The notebook found Decision Tree / Random Forest / XGBoost all reach a
  perfect F1 on this data. `train.py` deploys **Random Forest**
  specifically because its averaged votes across trees produce a graded
  `predict_proba`, which the frontend needs to show Low / Moderate / High
  risk bands rather than only 0% or 100%. A plain Decision Tree would
  return near-binary confidence on this cleanly-separable data.
- Risk bands: `probability < 0.34` → Low, `0.34–0.66` → Moderate,
  `>= 0.66` → High.
- This is trained on a **synthetic/mock dataset** for a classification
  project — not a validated clinical tool.
